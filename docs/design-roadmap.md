# 设计边界与后续路线

> 适用版本：`1.3.0-SNAPSHOT`；整理日期：2026-11-17。
>
> 本文记录**当前未接线能力、已知设计边界与后续候选工作**。候选工作不代表已经实现，也不承诺具体发布版本。使用方应以 [接入指南](content-safe-starter-guide.md)、[供应商能力矩阵](provider-feature-matrix.md) 和 [兼容政策](compatibility-policy.md) 描述的现有行为为准。

## 1. 已预留但未接线的抽象

以下类型虽然存在于源码中，但当前默认审核链路不会调用它们。仅声明对应 Spring Bean 不会使其生效。

| 类型 | 当前状态 | 后续处理原则 |
| --- | --- | --- |
| `ContentRefNormalizer` | 自 1.1.0 标记 `@Deprecated(forRemoval = true)`；core 与 provider 均无调用方 | 不在现版本直接接线。先明确对象存储转 URL、内容压缩等真实场景，再决定新版本预处理契约；若无稳定需求，在下一主版本移除 |
| `ProviderHealthProbe` | 自 1.1.0 标记 `@Deprecated(forRemoval = true)`；无后台调度器或健康注册表调用 | 不把它与现有 Actuator 健康端点混为一谈。若未来支持远程探测，应重新设计为默认关闭、后台异步、独立超时的可选能力 |
| `ProviderHealth` / `HealthStatus` | 仅服务于上述未接线探测抽象，已标记移除计划 | 与 `ProviderHealthProbe` 同周期处理；不要用于表达 `ProviderLifecycle` 的 ACTIVE/DEPRECATED/EOL 生命周期 |
| `ArbitrationStrategy` | 自 1.1.0 标记弃用；实际仲裁选择走 `AuditArbitrationPolicy`、注册表与场景选择器 | 保持现有仲裁体系，下一主版本清理重复枚举，不新增第二套路由逻辑 |

其他兼容负担：

- `DefaultContentSafeTemplate` 的旧构造器仅为二进制兼容保留，新代码使用 `builder()`。
- core 的旧 `security.ErrorMessages` 已弃用，统一使用 api 模块的 `util.ErrorMessages`。
- 上述弃用类型的移除必须遵守 [兼容与 Deprecation 政策](compatibility-policy.md)，不能在修订版本中直接删除。

## 2. 当前需要明确的生产边界

### 2.1 健康检查不是远程健康探测

当前 Actuator 健康端点展示本地熔断器、限流器、场景映射和操作构建状态，**不会主动请求云供应商**。因此：

- 健康端点为 UP 不等于云账号、网络或云端接口一定可用；
- 构造器和 `@PostConstruct` 不做同步远程探测；
- 云端可用性应结合审核指标、治理事件和业务告警判断。

### 2.2 默认治理和任务存储是单实例语义

- 默认 `InMemoryAuditTaskStore` 只保存当前 JVM 的任务；重启后丢失，多实例之间不共享。
- 默认令牌桶、并发信号量和熔断器也都是进程内状态，不提供集群级 QPS 或全局熔断。
- 多实例部署应提供共享 `AuditTaskStore`；需要全局限流时，应通过现有治理扩展点对接外部实现。
- 人审 `ReviewResultSink` 和外部任务存储仍需保证跨实例幂等，本地锁不能解决分布式重复副作用。

### 2.3 配置与凭证不是热刷新模型

- 长期凭证、供应商场景映射和 operation 对象在启动期定型；修改后需要重建应用上下文。
- 当前不承诺运行中轮换 AK/SK、动态增删场景或热更新 operation 配置。
- 火山引擎官方 SDK 客户端是进程级单例；默认实现检测到不同 AK 的重复初始化会失败。多账号应自定义 `VolcengineClientInvoker` 或拆进程，不能依赖配置热刷新。

### 2.4 超时声明不等于统一强制中断

`OperationLimits.timeout` 是操作元数据；core 不会用它统一中断供应商调用。实际硬超时由各 provider 的 SDK/HTTP 客户端配置决定。`submitAndWait` 的等待超时也不等于取消云端任务。接入新 provider 时必须分别核实连接、读取和异步等待语义。

### 2.5 回调安全能力取决于供应商

- 阿里云回调使用约定算法验签。
- 腾讯、百度、数美的已接入官方回调未提供签名机制，当前只做结构校验；接收侧仍应配置 IP 白名单、网络隔离等防伪措施。
- 验签或结构校验失败进入死信；任务关联和终态迁移保持幂等。

### 2.6 契约测试不替代云上联调

测试使用响应样本、Mock 和本地 HTTP 服务，不访问真实云接口。供应商字段、限额和服务生命周期仍可能变化，发布前应根据控制台与官方文档复核，并使用测试账号完成联调或灰度验证。

## 3. 后续候选工作（未实施）

按优先级评估，不在本文承诺交付日期：

1. **弃用契约清理**：下一主版本移除无调用方的重复抽象和兼容构造器，给出迁移说明。
2. **可选远程健康探测**：只有明确运维需求后再设计；必须默认关闭、后台执行、限制频率与超时，并对状态变化发事件，禁止启动期同步调用。
3. **分布式治理示例**：补充共享任务存储、集群限流和幂等人审回写的实现指引；不在 core 新建与现有 SPI 平行的体系。
4. **配置与凭证刷新**：先定义原子配置快照、进行中调用语义和失败回滚，再评估实现；火山顶单例限制必须单独处理。
5. **超时契约核查**：逐 provider 对照官方 SDK/HTTP 文档，区分声明值、实际传输超时与业务等待超时，避免“配置了但没有生效”。
6. **云端契约验证**：在不进入 CI、不泄露凭证的前提下增加可手动执行的沙箱验证流程，持续更新响应样本和能力矩阵。
7. **内容预处理能力**：只有出现稳定使用场景后才设计新契约；不为了“用完接口”而直接启用已弃用的 `ContentRefNormalizer`。
8. **新内容类型**：音频、文件、直播等仍属预留方向，须先完成官方接口调研、能力矩阵、限额和契约测试，不在业务代码中提前宣称支持。

## 4. 后续接线的统一验收条件

任何候选能力进入实现阶段时，至少满足：

- 复用现有 api/spi/model/core 抽象，不新增平行路由、归一化或治理体系；
- 保持启动轻量、能力先行、结果归一、证据脱敏和错误码稳定；
- 所有降级、探测失败和刷新失败可观测，不静默改变审核结论；
- 新逻辑包含单元测试；starter 包含 `ApplicationContextRunner`；provider 包含契约测试；
- 公共签名通过 japicmp，依赖方向通过 ArchUnit；
- 同步更新根 README、英文 README、接入指南、能力矩阵、错误码表及相关模块 README。
